# 文档写作规范

文档应让读者理解技术方案、限制和验证依据。准确性优先于简短。
本规范适用于公开文字；API 语法和引用内容保留原有拼写。

## 语言和证据

公开文档默认英文，并按[文档配对目录](document-pairs.json)提供完整的简体中文版本。
翻译时同步保留含义、约束、单位、版本和确定程度，不在任一语言中增加承诺。
内部笔记可以只用中文，保存在公开目录之外。

区分 API 文档中的限制、设计提案、计算估算和实测结果。
引用外部技术事实时，在相应段落附近链接一手资料。
报告性能时说明构建版本、测试条件、样本数、分位数和准确的起止事件，保留失败场景和未知项。
不要为了让改写显得具体而补造数字。

## 英文表达

- 直接说明问题或操作，优先使用具体动词，并指出负责的模块。
- 主动语态有助于说明所有权时优先使用。缓冲区、解码器和线程都可以作为主语。
  行为主体未知或无关紧要时，可以使用被动语态。
- 用 must 表示要求、should 表示建议、may 表示选项。
  表达实际限制的 usually、estimated 和 not yet verified 等限定语必须保留。
- 删除宣传性形容词、刻意铺垫、无必要的对比和重复总结。
  不要把完整解释压缩成口号或一串没有关系说明的名词。
- 有先后顺序时使用编号步骤，列举并列事项时使用项目列表。
  真实的三步流程无需强行改变句式；不全面禁止副词、疑问句、括号或三项列表。

## 中文表达

使用自然、现代的中文，优先写清动词和主语。每段围绕一个问题或决策展开，减少掩盖动作和
责任主体的名词化表达。读者需要的解释必须保留，不为缩短篇幅而省略。

检查“赋能”“抓手”等空话，以及没有证据的改善结论。
结合上下文检查刻意对比、模板化过渡、凑数排比和重复总结，不把示例词变成一律禁用的词表。
真实的技术比较、控制回路描述可以保留。删掉空话时，不删限定条件或证据。

中文句子用中文标点；完整英文句子、代码、标识符和 URL 保留英文标点。
中文与英文、数字之间留一个空格，包括行内代码和链接文字两侧。
官方名称和标识符内部不插入空格。
写作 `512 MiB`、`2 ms`、`90°`、`25%`，区分 GiB 和十进制 GB。
换行只影响排版，不得改变单位、公式或测量值。

## 术语与组织

采用[术语表](TERMINOLOGY.zh-CN.md)中的名称。
专业术语首次出现时，按读者背景简要解释；中文名称后可附英文术语。
API 名称使用行内代码，不翻译或改变 `ID3D11DeviceContext` 的大小写。

介绍项目概念时，说明它代表什么、为什么需要、由谁维护、何时创建、更新和释放，以及它与
相似概念的区别。能复用已有概念时，不新增术语。

设计文档应说明问题、运行流程、方案依据、限制、失败处理和验证方法。
按内容选择标题，不要求每页套用相同章节。线程、数据流和生命周期关系适合用 Mermaid 表达时，
配上必要的文字解释。图、表和正文必须一致，并明确当前实现状态。

## Markdown

- 使用 UTF-8、LF 和文件末尾换行。每页一个 H1，采用 ATX 标题，不跳过层级。
- 标题、列表、表格和围栏代码块前后留空行，围栏代码块注明语言。
- 仓库内使用描述清楚的相对链接，外部资料使用 HTTPS。
  公开页面不链接私人草稿、机器报告或本地绝对路径。
- 普通段落尽量在约 100 个字符处换行；URL、API 标识符和表格不强制断行。
- 命令和标识符使用反引号。表格用于比较，不用来排版大段文字。
- 页首提供语言切换链接，同时更新两种语言的修订元数据。

## 原始 Pixstride 草稿的改写示例

以下片段来自已保留的架构、渲染、性能和解码草稿，不含私人路径。
示例只调整表达，不改变技术决定。英文规范使用相同原文，提供含义对应的英文改写。

### 1. 讲清路由依据

原文：

> 普通图片不经过 Tile Builder。超大图片也不先分配全图 Bitmap 再尝试分块。
> 路由依据头信息、预测像素字节、单纹理限制和资源预算，不能只看压缩文件大小。

改写：

> 普通图片采用直接解码并上传的路径。读取文件头后，根据尺寸、预计解码字节数、纹理限制和
> 可用预算，决定是否转入超大图片路径。超大图片路径必须避免分配完整位图；压缩文件大小
> 不足以单独决定路由。

改写把决策过程写清楚，保留了四项依据和完整位图分配限制。

### 2. 保留线程方案的代价和实验条件

原文：

> 这不是“多线程一定更快”的结论。选择的依据是隔离驱动阻塞与 UI 响应，代价是一次唤醒。
> A 阶段测 GPU 命中端到端延迟，若线程切换显著损害 P95，先优化合并与唤醒，再重新评审。

改写：

> 独立渲染线程能将驱动阻塞与 UI 输入处理隔离，代价是多一次线程唤醒。
> 阶段 A 将测量 GPU 缓存命中的端到端延迟。如果额外线程使 P95 延迟明显恶化，先检查
> 通知合并和唤醒，再评审线程模型。

读者可以直接看到收益、成本和重新评审的条件，无需经过刻意对比。

### 3. 写清上传预算控制的行为

原文：

> 每轮上传初值 ≤16 MiB 或 CPU 提交预算 2 ms，先服务最新目标，再做预取。
> 这是停止提交更多任务的软预算，**不能抢占一个已经阻塞的驱动调用**。

改写：

> 初期每轮上传达到 16 MiB 或 CPU 提交耗时达到 2 ms 时，渲染线程停止提交后续上传。
> 最新目标的上传优先于预取。这是软限制，无法中断已经阻塞的驱动调用。

改写明确了操作主体和停止条件，也保留了无法中断驱动调用的例外。

### 4. 区分应用处理时间和显示延迟

原文：

> 50 ms窗口目标不能用“调用了ShowWindow”就判通过，外部窗口可见与首个合成帧要交叉验证。
> 缓存命中5 ms是处理目标，60 Hz屏幕无法保证每次实际屏显小于5 ms。

改写：

> 50 ms 的窗口可见目标，需要结合外部可见性观察和首个合成帧验证。
> 仅记录 `ShowWindow` 调用不能证明达标。缓存命中的 5 ms 指标测量应用处理时间，
> 不保证 60 Hz 显示器在 5 ms 内显示新画面。

两种测量边界分开描述，两个数值仍然是目标。

### 5. 先说明 PNG 的数据依赖

原文：

> 反过滤可能依赖上一行，Deflate还依赖滑动窗口；不能用`文件偏移+矩形`直接读任意区域。

改写：

> PNG 反过滤可能需要上一行的数据，Deflate 解压还需要滑动窗口状态。
> 因此，仅给出文件偏移和矩形范围，不足以解码任意区域。

改写说明了限制的来源，没有把增量输入改写成随机区域访问能力。

### 6. 保留取消时限的实验性质

原文：

> 取消每若干行/每个I/O块检查，目标协作退出≤100 ms；500 ms无回应可终止worker，
> 这些也是测试目标。

改写：

> 在扫描行批次和 I/O 块之间检查取消请求。初始目标是在 100 ms 内协作退出；
> 工作进程在 500 ms 后仍无回应时，可以终止。两个时限都需要测试验证。

检查时机、退出目标和超时处理分别说明，没有暗示已经测得这些时限。

## 发布前自审

- 目标读者能否理解运行流程，并找到各项资源的维护模块？
- API 名称、限制、单位、版本、异常路径和确定程度是否保留？
- 两种语言的要求和测量边界是否一致？
- 估算和计划行为是否与实测结果、当前行为分开说明？
- 是否已移除私人路径、凭据、本地日志和未经批准的图片？
- 链接、Markdown、配对元数据和工具检查是否通过？是否人工检查了提示和文字？

采用和调整了哪些规则，见[写作来源与许可核查](zh-CN/writing-sources.md)。
自动检查只能发现特定问题，不能证明文字易读或技术事实正确。
