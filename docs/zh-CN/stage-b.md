# 阶段 B：图片浏览核心

阶段 B 已通过 [PR #3](https://github.com/pachi-qwq/pixstride/pull/3) 合并，实现了打开 JPEG、PNG、BMP，浏览当前目录，并通过已有 D3D11 渲染线程显示解码像素。负责人已确认图片能正常显示、缩放操作有效、方向键可以切换图片、`Ctrl+O` 能打开原生文件对话框，窗口 Resize 时仍可响应。负责人复测 `ea23c91` 后也确认长按体验明显改善，下文保留实测数据和验证缺口；这些检查没有覆盖所有错误路径。

## 打开与导航

Pixstride 接受一个可选命令行图片路径，支持 Unicode 和包含空格的路径。按 `Ctrl+O` 打开 Windows 原生文件对话框。
Left 和 Right 在当前目录的支持文件之间导航，到达目录边界时停留在当前图片。按 `F` 选择 Fit to Window，按 `1`
选择原始像素尺寸。Fit 保持宽高比并居中显示。原始像素模式以 1:1 比例居中，超出客户区的部分会被裁切；普通图片路径尚未实现平移。
超大 PNG 的缩放/平移已在独立的 [阶段 C](stage-c.md) 路径中合并。

目录扫描只纳入扩展名为 `.jpg`、`.jpeg`、`.png`、`.bmp` 的普通文件。排序先比较 Unicode 小写文件名，再用原始文件名
打破平局，确保结果确定。目录扫描在图片工作线程执行，不阻塞 Win32 消息循环。

## WIC 与像素所有权

一个有界工作线程初始化 COM MTA，并在该线程创建和使用全部 WIC 对象。线程解码第 0 帧并返回自有字节缓冲区；WIC
COM 接口不会跨线程传递。WIC 将像素转换成 32-bit premultiplied BGRA（`GUID_WICPixelFormat32bppPBGRA`）。若能读取
EXIF Orientation 元数据，则将方向 1–8 映射为 WIC 翻转或旋转。渲染器把像素上传为
`DXGI_FORMAT_B8G8R8A8_UNORM`，并使用 premultiplied-alpha 混合，将透明像素合成到背景色上。

分配 `CopyPixels` 缓冲区前，程序使用溢出检查计算尺寸、行跨度和总字节数。当前默认值为单边不超过 16,384 像素、
单张解码数据不超过 256 MiB、CPU 与 GPU 常驻缓存各 512 MiB。这些值是可调整的代码初值，并非测得的最佳配置。
超过边长或解码字节预算的图片会在分配整张像素缓冲区之前被拒绝。48,000 × 32,000 压力 PNG 不属于此处理路径，
本轮没有打开它。

## 任务调度与缓存

UI 为每次选择变化维护一个单调递增的 `generation`。工作线程最多保存一个待处理的当前图片请求、一次目录扫描和
两个相邻预加载请求。新选择替换尚未开始的工作，活动 WIC 调用可以完成；不在已批准的同方向长按区间内的过期结果会丢弃。CPU LRU 由工作线程独占，以规范化路径、文件长度和最后修改时间作为缓存键。该键能识别常见文件替换，
但不是内容哈希。

渲染线程独占 D3D11 Texture LRU 和 Immediate Context。GPU 缓存命中时复用已上传纹理，按宽 × 高 × 4 字节计费，
将较旧的非当前纹理淘汰到 512 MiB 预算以内。CPU 缓存按实际像素缓冲区长度计费。一次解码可能在 CPU 常驻缓存之上
再占用最多 256 MiB；阶段 B 不使用临时磁盘缓存。

UI 将最新路径交给一个有界的文件身份校验线程。它只规范化路径并读取元数据，不使用 WIC。UI 再把已校验的选择
交给渲染线程查询纹理缓存。GPU 命中时直接激活纹理，不进入 WIC Worker、不查询 CPU 缓存、不解码，也不上传像素。
GPU 未命中才调度解码工作。WIC Worker 在查询 CPU 缓存前和解码完成后再次检查源修订。元数据校验只代表校验时刻：
检查后发生的修改可能在下次选择时才反映；长度和时间戳都未变化的内容修改仍可能碰撞。目前没有文件监听器。

各阶段都检查 UI 维护的选择 Generation。身份线程和 WIC Worker 各自只保留最新待处理选择；新 Generation 清除旧 GPU
探测请求，以及不符合长按进度条件的待提交像素。渲染器提交尚未呈现的候选图片前会再次检查 Generation。已经交给 DXGI 的帧无法撤回。
目录扫描会等待当前选择的 GPU 命中或解码调度决定，避免在这个决定之前启动。

新选择丢弃排队中的 GPU 预加载。渲染器先呈现当前选择，每次唤醒之后最多上传一张相邻纹理。WIC Worker 只在空闲
120 ms 后启动排队的相邻预加载；新选择重置延迟并优先处理。已经开始的 WIC 调用、元数据读取、目录扫描和纹理上传
无法抢占。缓存未命中仍可能等待正在执行的预加载；GPU 命中现在可以绕过这段解码等待。连续导航采用 Latest Selection Wins：
每次有效导航都改变目标索引，待处理请求可以合并，最终有效目标必须到达 `Present`。程序不承诺长按时呈现每个中间画面，
尤其是在存储或 WIC 处理慢于输入速率时。

当前图片读取、解码失败和目录扫描错误通过标题栏和 stderr 提示，导航可继续，不再弹出阻塞消息循环的错误框。
超预算图片仍会被安全拒绝；单图和两级缓存预算均未提高。

### 最终回归覆盖

常规测试为 47 项通过、3 项显式诊断。新增状态测试调用实际导航函数，检查同方向区间保持、突然反向，以及旧方向的松键
不能终止新方向。已有测试覆盖进度代际不倒退、待提交结果失效、预算拒绝复用和源修订变化。

扩展的 `release_navigation_cache_probe` 在当前请求完成 `CopyPixels`、尚未发布结果时暂停 Worker，分别触发较新 GPU
命中、`WM_KEYUP`、反向、`WM_KILLFOCUS` 和打开另一文件。每个 GPU 缓存目标都在闸门放行前到达 `Present`；之后旧解码
取消，不能覆盖目标。两个窗口消息在 HWND 所属线程同步注入。打开文件调用接收已选择路径的处理函数，没有自动操作原生
文件对话框。

同一诊断还修改生成 BMP 的实际像素和长度，检查缓存失效；删除源文件并检查非模态恢复；拒绝截断 JPEG。预算测试检查
提前拒绝、复用时跳过 WIC，以及源修订变化后重新尝试。全部样本由测试生成，保存在 Git 之外，不读取私人图片或不可用的云文件。

缓存与边界、长按进度和 JPEG 三项诊断均已分别通过 Release 重跑。格式、将警告视为错误的 Clippy、单元测试、Release
构建、Rustdoc、52 个公开文件的文档检查、41 项文档工具测试及 `git diff --check` 均通过。代码只增加测试；正式程序线程、
调度、资源所有权和 256 MiB / 512 MiB / 512 MiB 预算均不变。基础 GUI 和长按可用性改善已由负责人确认。物理键盘、
Alt+Tab 边界压力、真实云端阻塞中关闭、长期压力、Device Lost 注入、受控启动和显示帧测量仍未验证；消息注入与 Worker
闸门不能替代这些测试。

UI 收到导航 `WM_KEYUP` 时记录该时刻的目标 Generation。报告区分松键前已提交、松键后才提交、仍在等待，以及被后续输入

负责人复测 `e5c3a2a` 后仍观察到停顿。223 次目标变化只产生 73 次图片选择 `Present` 返回，77 个过期任务在阶段间取消。

`GetFrame`/EXIF 合计阶段最大 1.358 s，`CreateDecoderFromFilename` 最大 31.134 ms，`CopyPixels` 最大 303.545 ms。
这把一次长尾缩小到帧或元数据处理阶段，尚未确定底层原因。旧版只保留最近记录，较早的慢任务已被挤出，无法关联到具体文件。
该轮 54 个 GPU 命中样本仍较快：P50 3.475 ms、P95 4.263 ms、最大 4.413 ms。五个松键时未完成的目标均在
128.485 ms 内完成，最终目标和提交 Generation 均为 224。这些样本不能解释长按期间感受到的全部停顿。

负责人批准在长按期间放宽过期结果拒绝规则：同方向导航仍活动时，已经开始的当前图片解码可生成进度画面。UI 用已有
Generation 记录该方向允许的最早选择和最新目标，渲染器只接受区间内代际不倒退的图片。进度图片只改变显示内容和标题，
不改变目标索引或路径；标题注明已显示路径与待加载目标。待处理请求仍合并，不逐张排队，也不降低按键响应频率。

松键、反向、失去焦点和打开文件都会关闭旧区间。最新目标继续加载，之后不能再接受旧结果作为进度图片。较新的 GPU
缓存命中激活后，也禁止旧解码覆盖它。全部 GPU 资源仍由渲染线程拥有，已提交给 DXGI 的帧无法撤回。过期进度候选的错误
不会提示；当前目标的错误仍用非模态方式报告。未缓存的最终目标仍可能等待同步 WIC 调用；超预算目标会报错，不显示新像素。

现在先在 `GetFrame` 后检查原始尺寸，再读取 EXIF；`GetFrame`、EXIF 查询和预算预检分别计时。Worker 最多按已校验的
源修订保留 32 条明确的预算拒绝，重复选择未改变的文件可跳过 WIC。长度或时间戳变化后重新尝试。云文件、读取失败和
损坏文件错误不放入预算拒绝缓存，弱元数据键的限制仍存在。16 条任务记录改为保留最近 8 条及最多 8 条更早的慢记录，
避免重复的快速错误挤掉秒级长尾。

Release 测试 `release_hold_navigation_probe` 使用 40 张生成的 64 × 64 BMP 和 Hardware D3D11。在 `CopyPixels`
之后注入 80 ms 不可抢占工作，每约 20 ms 更新目标，两个方向各一轮，检查进度显示与松键后的最终目标。测试专用的严格
Generation 模式关闭进度区间，作为旧丢弃策略的参照。每种模式只运行一轮，未控制启动、系统调度或缓存差异；没有注入真实
键盘事件，也没有读取私人图片或云文件。

| 同一注入负载 | 严格 Generation 参照 | 进度显示 |
|---|---|---|
| 目标变化 | 60 | 60 |
| 图片选择 `Present` 返回，含首图与最终图 | 4 | 23 |

缓存回归也已重跑：103 个 GPU 命中选择到 `Present` 返回为 P50 762 μs、P95 7,160 μs、P99 8,015 μs、最大 9,988 μs。

运行间变化也说明结论有限。

### 连续导航人工对照

分别使用本地 SSD 和已完整下载的 OneDrive 目录，测试同一组经过审核的小型 JPEG、PNG、BMP。记录云文件可用状态与
存储位置，不从盘符推断存储类型。启动 Release 程序，等待首图与相邻预加载完成，分别运行：30 次短按往返、每个方向长按
3 秒，以及快速反向。每轮松键后记录目标文件名，核对最终图片，等待后正常关闭，保存计时。样本集中可包含一张超预算图片，
确认标题栏报错后无需关闭弹窗就能继续导航。长按时检查进度图片是否沿同方向前进，松键、反向或失焦后检查旧进度是否停止，
并对比新增进度计数。只有负责人接受相应读取或下载行为时，才另外测试已知不可用的云文件。

对比身份校验、已有预加载时的排队、当前与预加载 WIC 服务时间、GPU 命中与未命中到 `Present`、目标变化、提交选择和
缓存峰值。纯 GPU 命中跳过 WIC 和 CPU 查询；CPU 命中仍经过单个 WIC Worker，若 GPU 条目被淘汰还需上传纹理。
持续长按已有上文负责人实测证据；受控云端长尾、真实目录 GPU 淘汰后的 CPU 命中分布、真实长时间云文件或 WIC 调用中关闭，
以及 120 ms 预加载策略的受控对照，仍需进一步运行验证。`Present` 返回是应用内部边界，显示帧时间需要另外采集。

自动化测试覆盖路径排序与边界、尺寸和预算检查、EXIF 映射、CPU 缓存淘汰、过期 Generation 替换、排队预加载取消、视口尺寸，
以及拒绝截断 JPEG 数据、通过 WIC 解码生成的 BMP，以及通过 WIC 编码并解码运行时生成的 JPEG/PNG。负责人已人工确认
真实图片显示、缩放、方向键导航、文件对话框和 Resize。
慢速或云端文件读取、解码长时间运行时快速反向导航、WIC 调用进行中关闭窗口仍需进一步人工验证。WIC 调用是同步的，开始后
无法取消。关闭时，Pixstride 会请求取消并等待最多 2 秒；如果某个 Worker 仍阻塞在 WIC 或文件系统调用中，程序会分离该线程并退出进程，
由 Windows 回收进程资源。此处理限制了应用关闭等待时间，但无法在进程运行期间安全中断 WIC。负责人遇到 OneDrive 图片不可用时，
Windows 返回 `The cloud file provider is not running.`；Pixstride 未修改该文件，云文件提供程序的可用性不由解码器控制。
Device Lost 恢复、长期稳定性、平移、GIF、TIFF、WebP、RAW、AVIF、HEIC、JPEG XL、超大图分块和磁盘缓存仍未验证或不属于本阶段。
