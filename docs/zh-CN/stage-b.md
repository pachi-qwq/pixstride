# 阶段 B：图片浏览核心

阶段 B 实现了打开 JPEG、PNG、BMP，浏览当前目录，并通过已有 D3D11 渲染线程显示解码像素。负责人已确认图片能正常显示、缩放操作有效、方向键可以切换图片、`Ctrl+O` 能打开原生文件对话框，窗口 Resize 时仍可响应。这些检查没有覆盖所有错误路径，也不能据此确定性能百分位。

## 打开与导航

Pixstride 接受一个可选命令行图片路径，支持 Unicode 和包含空格的路径。按 `Ctrl+O` 打开 Windows 原生文件对话框。
Left 和 Right 在当前目录的支持文件之间导航，到达目录边界时停留在当前图片。按 `F` 选择 Fit to Window，按 `1`
选择原始像素尺寸。Fit 保持宽高比并居中显示。原始像素模式以 1:1 比例居中，超出客户区的部分会被裁切；目前未实现平移。

目录扫描只纳入扩展名为 `.jpg`、`.jpeg`、`.png`、`.bmp` 的普通文件。排序先比较 Unicode 小写文件名，再用原始文件名
打破平局，确保结果确定。目录扫描在图片工作线程执行，不阻塞 Win32 消息循环。

## WIC 与像素所有权

一个有界工作线程初始化 COM MTA，并在该线程创建和使用全部 WIC 对象。线程解码第 0 帧并返回自有字节缓冲区；WIC
COM 接口不会跨线程传递。WIC 将像素转换成 32-bit premultiplied BGRA（`GUID_WICPixelFormat32bppPBGRA`）。若能读取
EXIF Orientation 元数据，则将方向 1–8 映射为 WIC 翻转或旋转。渲染器把像素上传为
`DXGI_FORMAT_B8G8R8A8_UNORM`，并使用 premultiplied-alpha 混合，将透明像素合成到背景色上。

分配 `CopyPixels` 缓冲区前，程序使用溢出检查计算尺寸、行跨度和总字节数。当前默认值为单边不超过 16,384 像素、
单张解码数据不超过 256 MiB、CPU 与 GPU 常驻缓存各 512 MiB。这些值是可调整的代码初值，并非测得的最佳配置。
超过边长或解码字节预算的图片会在分配整张像素缓冲区之前被拒绝。48,000 × 32,000 压力 PNG 不属于此处理路径，
本轮没有打开它。

## 任务调度与缓存

UI 为每次选择变化维护一个单调递增的 `generation`。工作线程最多保存一个待处理的当前图片请求、一次目录扫描和
两个相邻预加载请求。新选择会替换尚未开始的工作；已经进入 WIC 的调用会运行到返回，若其 `generation` 已过期，
结果会丢弃。CPU LRU 由工作线程独占，以规范化路径、文件长度和最后修改时间作为缓存键。该键能识别常见文件替换，
但不是内容哈希。

渲染线程独占 D3D11 Texture LRU 和 Immediate Context。GPU 缓存命中时复用已上传纹理，按宽 × 高 × 4 字节计费，
将较旧的非当前纹理淘汰到 512 MiB 预算以内。CPU 缓存按实际像素缓冲区长度计费。一次解码可能在 CPU 常驻缓存之上
再占用最多 256 MiB；阶段 B 不使用临时磁盘缓存。

当前 GPU 缓存命中仍需等待 WIC 工作线程规范化路径、读取文件元数据并查询 CPU 缓存，渲染器之后才能识别已缓存纹理。
CPU 缓存命中会跳过 WIC 像素解码，但仍需经过工作线程交接和源文件版本检查。把这项检查留在后台可避免 UI 线程阻塞，
也能防止文件修改后显示过期纹理。用户切换图片时，程序会丢弃尚未上传的旧 GPU 预加载项。渲染器先显示当前选择，之后
每次唤醒最多上传一张相邻图片纹理；队列最多保存两张。已经开始的纹理上传无法抢占。
解码 Worker 在选择图片或更新预加载队列后，会延迟 120 ms 再开始排队的相邻预加载。新的当前图片请求会立即唤醒
Worker 并优先处理。这是调度实验，目的是避免连续操作期间启动推测性的 WIC 工作；已经进入 WIC 的预加载仍无法中断。

## 诊断和限制

退出时，现有有界计时器汇总目录扫描、WIC 打开、格式转换器初始化、`CopyPixels`、成功解码总耗时、纹理上传、渲染线程
请求延迟、首张图片 `Present` 返回，以及 CPU/GPU 缓存命中数和当前/峰值常驻字节数。字节数只统计缓存拥有的条目，不含进程工作内存
或驱动额外分配。文件读取由 WIC 管理，因此当前版本不能将存储延迟与解码工作分开。
`Present` 返回是应用内部测量边界，不代表光子已到达显示器。

当前诊断版本还会分别统计当前选择与预加载的 CPU/GPU 命中和未命中、源文件身份检查与 CPU 缓存查询耗时、当前图片请求
到工作线程返回结果的耗时，以及 GPU 命中和未命中两类“选择图片到 `Present` 返回”分布。GPU 命中仍需经过上文所述的工作线程检查。
命中率只以成功完成缓存查询的请求为分母；文件身份、解码或上传失败会单独报错，不计为缓存未命中。
负责人此前一次运行的总计数为 CPU 命中/未命中
26/13、GPU 命中/未命中 26/5，包含预加载；该次总命中率分别为 66.7% 和 83.9%，不能代表纯导航命中率。11 个图片请求到
渲染线程样本的 P50 为 202 μs，最大值为 161.58 ms。之后一次负责人使用真实本地目录运行，共记录 78 个当前图片请求和
143 个预加载请求。当前选择的 CPU 命中为 73/78（93.6%），GPU 命中为 66/76（86.8%）；预加载 CPU 命中为
66/143（46.2%），GPU 命中为 65/134（48.5%）。分母只计入成功完成的缓存查询；源文件检查或上传失败不计为缓存未命中。

该次运行的源文件身份检查与 CPU 缓存查询耗时为 P50 3.072 ms、P95 4.153 ms。当前图片请求到 Worker 返回结果为
P50 3.472 ms、P95 126.214 ms，最大 376.136 ms。当前 GPU 命中从选择图片到 `Present` 返回为 P50 3.456 ms、
P95 4.305 ms；GPU 未命中为 P50 51.537 ms、P95 177.570 ms。WIC 完整解码耗时为 P50 48.462 ms、P95 212.795 ms；
预加载解码最大耗时为 1.205 s。CPU 与 GPU 缓存拥有的峰值字节数各约 511.5 MiB，接近各自 512 MiB 预算；这些数值
不代表进程总 RAM 或驱动实际占用的 VRAM。

请求到 Worker 的长尾明显高于缓存查询耗时，这与单个 Worker 正在执行同步 WIC 读取或解码的情况一致。现有汇总数据没有
单独测出队列等待和 WIC 执行时间，因此不能据此确认每个长尾样本的具体原因。上文的 120 ms 空闲延迟用于减少连续导航时
预加载对当前请求的干扰；它不能中断正在执行的 WIC 工作，效果仍需负责人再次实测。`Present` 返回耗时仅是应用内部指标，
不代表帧已显示，也不代表 Input-to-Photon 延迟。这些数据用于诊断，不是受控基准测试。

自动化测试覆盖路径排序与边界、尺寸和预算检查、EXIF 映射、CPU 缓存淘汰、过期 Generation 替换、排队预加载取消、视口尺寸，
以及拒绝截断 JPEG 数据、通过 WIC 解码生成的 BMP，以及通过 WIC 编码并解码运行时生成的 JPEG/PNG。负责人已人工确认
真实图片显示、缩放、方向键导航、文件对话框和 Resize。
慢速或云端文件读取、解码长时间运行时快速反向导航、WIC 调用进行中关闭窗口仍需进一步人工验证。WIC 调用是同步的，开始后
无法取消。关闭时，Pixstride 会请求取消并等待最多 2 秒；如果 Worker 仍阻塞在 WIC 调用中，程序会分离该线程并退出进程，
由 Windows 回收进程资源。此处理限制了应用关闭等待时间，但无法在进程运行期间安全中断 WIC。负责人遇到 OneDrive 图片不可用时，
Windows 返回 `The cloud file provider is not running.`；Pixstride 未修改该文件，云文件提供程序的可用性不由解码器控制。
Device Lost 恢复、长期稳定性、平移、GIF、TIFF、WebP、RAW、AVIF、HEIC、JPEG XL、超大图分块和磁盘缓存仍未验证或不属于本阶段。

在 Windows 10/11 x64、已安装 MSVC 和 Windows SDK 的环境中构建：

```powershell
cargo build --release --locked
cargo run --release -- "<image-path>"
```

不提供路径时，程序使用阶段 A 生成的测试纹理启动。运行 `cargo run --release` 后按 `Ctrl+O` 选择图片。标题栏显示当前路径。
构建检查及当前验证状态见[开发说明](../en/development.md)。
